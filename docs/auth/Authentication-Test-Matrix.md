# Authentication test matrix

This is the release checklist for HYPE authentication. It covers the flows
implemented today; it is not a proposed product-policy matrix. Mark the result
column as **Pass**, **Fail**, **Blocked**, or **Not applicable** for the
environment tested, and attach the browser/device, hub host, and error details
to every failure.

For role-based content and admin permissions, use
[Policy Matrix.md](./Policy%20Matrix.md) alongside this document. That matrix
covers resource authorization after a durable account has authenticated.

## Scope and current availability

| Method or capability             | Current state                                                                 | Where it is exposed                                               | Important expectation                                                                                                |
| -------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Anonymous guest                  | Implemented                                                                   | Interactive app routes and `/signin`                              | A guest gets a temporary session and may later upgrade without losing supported state.                               |
| Email and password               | Implemented                                                                   | `/signin`, `/signup`, account-upgrade UI, profile linked accounts | Sign-up requires a name; email verification is required.                                                             |
| Google OAuth                     | Implemented when `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET` are configured     | Auth entry and profile linking                                    | The UI is enabled, but a deployment without both credentials cannot complete the flow.                               |
| Facebook OAuth                   | Implemented when `AUTH_FACEBOOK_ID` and `AUTH_FACEBOOK_SECRET` are configured | Auth entry and profile linking                                    | Facebook is a trusted provider for verified-account linking; provider identity cannot belong to two HYPE users.      |
| Passkey                          | Implemented                                                                   | Auth entry, guest upgrade, and profile linked accounts            | The RP ID and origin are derived from the current host, so each production/preview/custom-domain host needs testing. |
| Password reset                   | Implemented                                                                   | Email sign-in panel and `/account/reset-password`                 | A successful reset revokes existing sessions.                                                                        |
| Add email/password to an account | Implemented                                                                   | Profile linked accounts                                           | Adds the first credential only; it must not overwrite an existing password.                                          |
| Link/unlink social accounts      | Implemented                                                                   | Profile linked accounts                                           | The UI must retain at least one linked `account` record.                                                             |
| Add/remove passkeys              | Implemented                                                                   | Profile linked accounts                                           | Removing the last passkey is blocked only when there is no linked account method.                                    |
| WeChat                           | Intentionally unavailable                                                     | Auth entry                                                        | It is displayed disabled with “coming soon”; do not record it as a regression.                                       |

## Test accounts and setup

Use fresh, unique email aliases for each run. Do not reuse a social identity in
two test accounts: Better Auth correctly treats that as an account-linking
conflict.

| ID  | Persona                 | Minimum setup                                                                                                                                                    | Use for                                                              |
| --- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| U   | Unauthenticated visitor | New browser profile; no HYPE cookies                                                                                                                             | Public access, automatic guest bootstrap, login/signup.              |
| G   | Guest                   | Start at an interactive app route and wait for the anonymous session                                                                                             | Guest persistence and every guest-upgrade route.                     |
| E   | Verified email account  | Create and verify an email/password account                                                                                                                      | Password sign-in/reset, adding passkey/social methods, logout.       |
| GGL | Google-only account     | Complete Google OAuth; no password initially                                                                                                                     | Google sign-in, linking and adding credentials.                      |
| FB  | Facebook-only account   | Complete Facebook OAuth; no password initially                                                                                                                   | Facebook sign-in, linking and adding credentials.                    |
| PK  | Passkey-only account    | Create via guest-to-passkey upgrade, ideally without an email                                                                                                    | Passkey sign-in, optional email verification, credential management. |
| M   | Multi-method account    | E plus Google/Facebook and a passkey                                                                                                                             | Link/unlink and method-removal safeguards.                           |
| R   | Role test accounts      | Durable account per applicable role: core admin, scoped hub admin, organisation owner/member, project owner/maintainer/translator/member/user, unrelated account | Apply the companion authorization matrix.                            |

Before testing, confirm the selected host is an entry in `trustedOrigins`; for
OAuth, its provider callback URL must also match the host. Test every host that
will be released: core production, preview, each hub subdomain/custom domain,
and local development as applicable. Passkeys must be tested using HTTPS (or a
browser-approved secure local origin) and a genuine platform authenticator or
password manager.

## Account-state matrix

Use this table to choose the correct expected outcome before each scenario.

| Scenario                                               | U                                        | G                                                          | Durable account (E/GGL/FB/PK/M)                                    |
| ------------------------------------------------------ | ---------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------ |
| Visit an interactive app route                         | A guest session is created client-side   | Resume the same guest                                      | Resume signed-in account                                           |
| Visit `/signin` or `/signup`                           | Stay on auth entry                       | Stay so the guest can upgrade or sign in                   | Redirect to safe `returnTo`, otherwise `/`                         |
| Read published, non-archived public content            | Allowed                                  | Allowed                                                    | Allowed                                                            |
| Read unpublished/archived content                      | Denied unless a separate role allows it  | Denied                                                     | Depends on role and scope                                          |
| Create a contribution or access an account-only action | Upgrade/sign-in prompt                   | Upgrade prompt; server result should be `ACCOUNT_REQUIRED` | Depends on role and scope                                          |
| Visit `/admin`                                         | Redirect to `/?upgrade=admin&returnTo=…` | Same redirect                                              | Allowed only when authorization permits the requested admin action |
| Open a profile                                         | Sign in/guest route                      | Upgrade prompt                                             | Open own profile                                                   |
| Hold roles                                             | No                                       | No; guest sessions always have no roles                    | Yes, when assigned in the database                                 |
| Sign out                                               | Not applicable                           | Ends the guest session and lands on `/signin`              | Ends the account session and lands on `/signin`                    |

## Roles and authorization follow-through

Authentication proves who the person is; it does not grant resource access.
For every durable role account in R, run the relevant **Allow** and **Deny**
cells from [Policy Matrix.md](./Policy%20Matrix.md), at minimum for:

| Resource area             | Required scenario coverage                                                                                                                   |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Hub                       | List/read published, unpublished, and archived; create/update/publish/delete; role management; core vs same-hub vs other-hub administration. |
| Organisation              | List/read each state; create/update/publish/archive; role management; core/scoped hub field restrictions.                                    |
| Project                   | List/read each state; create/update/publish/archive; i18n-only translator update; role/capability management; moving across organisations.   |
| Layer and feature         | Public vs unpublished/archived visibility; create/update/publish/archive; translator field limits; maintainer/owner escalation.              |
| Tasks, images, properties | Read/list scope and every write/assignment/upload action used by the release.                                                                |

For every denied server mutation, assert both that the UI blocks it and that a
direct request is denied with the documented authorization code (for example
`UNAUTHENTICATED`, `ACCOUNT_REQUIRED`, `INSUFFICIENT_ROLE`, or a scope/field
code). Verify the record did not change.

## Existing automated coverage and gaps

The following tests give useful regression coverage, but they do **not** prove
provider email delivery, provider configuration, browser passkey UX, or the
full guest-state migration against a real D1 database:

| Area                                                       | Existing automated checks                                                                                                |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Auth configuration and OAuth fallback                      | `src/tests/auth.config.test.ts`                                                                                          |
| Auth entry redirects                                       | `src/tests/signin-page.test.ts`                                                                                          |
| Guest bootstrap, route exclusions, and guest authorization | `src/tests/anonymous-bootstrap.test.ts`, `src/tests/anonymous-authorization.test.ts`, `src/tests/redirect-guard.test.ts` |
| Guest retention cleanup                                    | `src/tests/anonymous.server.test.ts`                                                                                     |
| Passkey promotion/session refresh                          | `src/tests/passkey-upgrade.test.ts`, `src/tests/account-passkey.test.ts`                                                 |
| Add-password endpoint protections                          | `src/tests/account-password.test.ts`                                                                                     |
| Email content                                              | `src/tests/auth-email.test.ts`                                                                                           |
| Resource authorization                                     | `src/tests/authorization.*.test.ts` and corresponding `*.remote.test.ts` files                                           |

High-value additions after this manual pass are browser E2E coverage for the
email verification/reset cycle, each available OAuth provider, guest-state
migration, cross-host passkeys, and link/unlink/removal safeguards.
