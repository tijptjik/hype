# Hong Kong routing runtime experiment — 2026-10-18

Refs [EXT-1 #213](https://github.com/tijptjik/hype/issues/213), parent
[#186](https://github.com/tijptjik/hype/issues/186), and
[technical domain](../../spec/breadline/proposal/09-enhancements.md).
The [machine-readable results](routing-2026-10-18.json) retain the original 1,314 route samples plus subsequent smaller-instance runs,
failures, route hashes, graph identity, configurations and selected platform
telemetry. The [transit inventory](routing-transit-inventory-2026-10-18.json)
records the downloaded GTFS source and OSM relation counts.

Native Valhalla is the preferred production candidate from this experiment.
The dedicated token resolved the initial Containers permission blocker, and the
native application is deployed and serving routes. An alternating deployed
comparison recorded 468 requests from the same client, with NRT reported by both
Worker endpoints. Native had lower warm medians and substantially lower tail
latency. This is a single-client benchmark, not a global or mobile latency claim.

## Deployed comparison after token setup

The comparison in this section used `standard-2` (6 GiB). The later custom-size
experiment and current intent-triggered lifecycle are recorded below.

Ten warm repetitions per route/mode, plus first-use sweeps and four/eight-call
walking batches. Timing includes the full HTTP/JSON response; route-result
caching is disabled. Both backends use identical graph bytes. The final WASM
variant clears search reservations; native retains its baseline search settings.

| Mode | Native warm p50 / p95 | WASM warm p50 / p95 |
| --- | --- | --- |
| Walking | 148 / 250 ms | 225 / 405 ms |
| Cycling | 138 / 357 ms | 166 / 404 ms |
| Car | 140 / 244 ms | 200 / 2,886 ms |

At eight concurrent walking callers, p95 was 427 ms native versus 3,107 ms WASM.
Native returned successful routes for all 223 routable requests and consistently
rejected the 11 unreachable bicycle requests. WASM completed 222 routable requests,
with one queue timeout; the unreachable bicycle case returned six valid no-route
responses and five memory-exhaustion errors. All 17 successful first-use route/mode
pairs matched geometry hashes, summary and maneuver count across deployed engines.

The first verified native route after initial provisioning took 2,666 ms. That
initial request is separate from explicit stopped-container measurements below.
Five verified stopped starts all succeeded, with a 1,466 ms median and a
997–6,675 ms range, excluding shutdown time. Each sample records a `stopped`
state before the request. An early signal-only trial was excluded: SDK `stop()`
sends SIGTERM without waiting for termination. The corrected benchmark endpoint
awaits `destroy()` and returns the stopped state. This variation supports keeping
an instance warm during active use when latency is the priority.

Deployed motor-scooter routing also passed all 24 requests, with a warm median of
218 ms and p95 of 272 ms in its separate run. The native no-route response was
explicitly confirmed as error 442; the runner now retains wrapped native errors.
The native application uses one routing thread on `standard-2` (one vCPU, six GiB),
with a five-minute idle timeout. The dedicated deployment token is kept in a
Git-ignored, owner-only local file. Its value is excluded from benchmark artifacts.

- Native image: Valhalla 3.8.3, pinned to
  `sha256:70b45295d81035e3562e1bbf996a28d5fc55e1ccc5d7e3fff9f297d3b1a1359f`.
  The official 3.8.3 tag resolves to the WASM engine's pinned source revision,
  `a60c7cbfc83e073f50887cd27e0109d02e6b64e5`.
- WASM package: `valhalla-server@0.2.1`; source/validator checkout
  `53db62e78891b51e06600ed6369005c975ce5835`.
- Source: SaanSeoi October 1 HK PBF, SHA-256
  `470c2396f11f2e4d689260ddc5583dea215133773097b93f2f508a10d7fbdd63`.
- Shared graph: 57,733,120 bytes, 20 tiles; largest tile 36,294,136 bytes.
  Graph SHA-256:
  `bffb075aa6ce298052e6bc7154420b275bbdcb776601d1fbbc7abedb8e4b1bef`.
- Six public-coordinate journeys: Central–Sheung Wan, Mong Kok–Yau Ma Tei,
  Wan Chai–Causeway Bay, Sha Tin–Tai Po, Central–Tsim Sha Tsui and Central–Peak.
  Each is tested for walking, cycling and car. Scooter has a separate native run.
- Native runs locally with one routing thread, one CPU and one GiB memory.
  WASM runs in local workerd/R2 simulation and on a deployed Cloudflare Worker
  with a private R2 binding. Client timings use Bun fetch and include the complete
  JSON body; this is not a browser/mobile UI or multi-region client benchmark.
- No route-result cache. Baseline engines share 64 MiB decoded graph-cache
  settings and 16,384 search reservations. Snapping is 30 m and minimum reachability
  is zero to match the SDK's forced options. These simplified snapping settings
  require separate production-quality validation.
- No GTFS, elevation, live traffic or admin/timezone databases were imported.
  This cannot establish timetable routing, hill-aware costs, country access
  defaults or time-dependent restriction correctness. Car ETAs are estimates.
- The local native and WASM engines matched exactly for all 17 successful
  route/mode combinations on summary, encoded geometry hash and maneuver count.
  This establishes parity for the corpus, not ground-truth navigation quality.

## Warm local response times

Five repetitions per route/mode; successful samples only, with failures retained
separately. These include localhost HTTP and, for WASM, the Worker wrapper.

| Mode | Native p50 / p95 | WASM p50 / p95 | Successful samples per engine |
| --- | --- | --- | --- |
| Walking | 4.7 / 11.9 ms | 23.5 / 78.4 ms | 30 / 30 |
| Cycling | 8.1 / 17.7 ms | 8.5 / 41.9 ms | 25 / 30 |
| Car | 8.0 / 12.1 ms | 15.0 / 320.6 ms | 30 / 30 |
| Motor scooter | 6.6 / 16.7 ms | Not exposed by SDK | 18 / 18 native |

At eight concurrent walking callers, local p95 was 40.3 ms native versus
277.1 ms WASM. Native's warm engine has more latency headroom, but network and
container startup/placement still need deployed measurement.

Five forced local process restarts took 319–331 ms including Docker restart,
readiness and the first route. The graph/image were already local and the old
process's graceful shutdown delay was excluded. These are not Cloudflare
container cold-start timings.

## Deployed WASM response times

The baseline run used three warm repetitions; a second run used five and lowered
search reservations to 4,096 with reservation clearing after each route. Both
used a 96 MiB WASM memory ceiling and 64 MiB graph-cache budget. Baseline requests
reported NRT as the serving colo; this is not a measured HKG-to-HKG deployment.

| Mode | Baseline p50 / p95 | Search-memory variant p50 / p95 |
| --- | --- | --- |
| Walking | 213 / 442 ms | 243 / 442 ms |
| Cycling | 164 / 471 ms | 212 / 439 ms |
| Car | 182 / 2,195 ms | 209 / 3,729 ms |

The first verified route with a newly initialized engine took 7,676 ms client
wall time. It fetched three graph tiles totaling 44,283,968 bytes. Later newly
initialized isolates also incurred seconds of latency. At eight concurrent
walking callers, p95 was 3,195 ms baseline and 3,728 ms in the second run.
First-use sweeps and repeated sweeps are reported separately; the latter can
still encounter fresh isolates or engines reset after memory failure.

The Central–Tsim Sha Tsui bicycle pair has no path in this graph. Native
consistently reports no route. Across the two deployed WASM runs, the same pair
returned five valid no-route errors and five `RESOURCE_LIMIT` errors instead.
Each deployed run also had one `QUEUE_TIMEOUT` on an otherwise routable walking
request. Successful timings must not hide these failures. WASM heap capacity
reached its 96 MiB ceiling; that metric excludes JavaScript and platform overhead.

Lowering search reservations and clearing them between routes did not resolve
the failure. A local 48 MiB graph-cache experiment was worse: all six attempts
at the unreachable bicycle pair exhausted search memory. The final deployed
variant retains a 64 MiB graph cache. It is an experiment, not a production fix.

## Initial Cloudflare Container deployment blocker — resolved

The initial native Worker and Docker image build passed, and the Worker uploaded. The
subsequent request to `/accounts/<account>/containers/me` returned HTTP 403,
Cloudflare code `10000`, `Authentication error`. Container application/image
provisioning did not complete on that attempt. A new dedicated token subsequently
returned HTTP 200 from the Containers API; image publication, application creation
and successful native route responses are now verified. The benchmark secret is
configured on both deployed Workers.

The deployed comparison above resolves this blocker. The application ID is
`a0331314-44fe-4d64-9bb0-118a128d0028`, and the successful native Worker version is
`014a7b05-d8e0-4485-8429-8c0e6c41aee9`. Explicit stopped starts are recorded separately
from warm requests using corrected stop-endpoint version
`fdaebc73-c6c1-48aa-b016-b77d22396a4a`. Dedicated HK/mobile clients and container placement tuning
remain useful follow-up work; NRT is the Worker ingress colo, not proof of the
container host's physical location.

Local agent-started runtime processes were stopped after the experiment. The
authenticated WASM Worker, deployed native Worker/container application and dedicated private R2
benchmark bucket remain available for further experiments. Hype's
application Worker, production databases and application UI were not changed.
The deployed native instance was explicitly terminated after measurement and its
stopped state was verified; a later request will start it again.

## Smaller container and intent warm-up

Cloudflare accepted custom **1 vCPU / 3072 MiB RAM / 2000 MB disk** on this
account. Worker version `8472d8e9-75eb-4423-8920-b8c8ee0a3d3e` uses one shared,
on-demand instance with `sleepAfter = '2m'`. The configured maximum of two is a
capacity ceiling; there is no always-warm pool or per-user container.

The smaller instance completed all 223 routable corpus requests. Eleven expected
cross-harbour bicycle failures remained valid no-route responses. All 17
successful first-use pairs matched the original native summary, shape hash and
maneuver count. This run followed the earlier 6 GiB comparison, so timing changes
cannot be attributed solely to RAM or disk size.

| Mode | 3 GiB warm p50 / p95 | Earlier 6 GiB warm p50 / p95 |
| --- | --- | --- |
| Walking | 196 / 248 ms | 148 / 250 ms |
| Cycling | 187 / 439 ms | 138 / 357 ms |
| Car | 183 / 272 ms | 140 / 244 ms |

Eight concurrent walking requests had 270 ms p50 / 695 ms p95 (earlier 6 GiB:
427 ms p95). The separate scooter run passed 24/24, with 218 / 346 ms warm
p50/p95. Five isolated, verified stopped starts passed: median **3,254 ms**, range
**1,000–6,653 ms**, excluding shutdown. An overlapping cold/scooter trial was
excluded and both measurements repeated independently. These tests establish
bursts of eight, not a sustained production throughput or demand forecast.

`POST /warmup` needs no route parameters and resolves when the service port is
ready. The future UI can issue it at navigation intent and immediately collect
parameters. `POST /route` independently starts/waits if warm-up was skipped,
still running or expired. Completed requests and warm-ups refresh the shared
120-second idle window; active route responses defer expiration. Idle expiry
awaits `destroy()` to avoid Valhalla's lingering SIGTERM drain. `GET /state` is an
authenticated passive diagnostic. No cron or heartbeat keeps the engine warm.

The current Directions button continues to open Google Maps. Connecting a future
in-app flow needs an authorized app-server proxy or service binding, plus app
rate limits; the benchmark token must remain server-side. Production UI, graph
updates and transit planning are not completed by this lifecycle experiment.

Live lifecycle assertions passed. Two simultaneous warm-ups became ready in
1,522/1,527 ms while a concurrent cold route also succeeded. A subsequent route
reset the deadline; the engine remained healthy past the original deadline and
stopped **120.166 seconds** after that route completed. An abandoned warm-up
stopped **120.044 seconds** after its acknowledgement despite passive polling.
A route sent after that automatic stop, without warm-up, succeeded in **1,775 ms**.
Final explicit cleanup and a passive read both verified the stopped state. Full
timestamped events are included in the machine-readable results.

### On-demand cost model

Using [current Container rates](https://developers.cloudflare.com/containers/platform/pricing/),
provisioned RAM plus disk costs **$0.027504 per running hour**, before included
allowances. A two-minute idle tail costs about **$0.000917**; 1,000 non-overlapping
abandoned warm-ups would therefore cost about **$0.92** in idle-tail RAM/disk,
plus startup, CPU and any time spent collecting parameters. Overlapping sessions
share uptime; they do not each start a separate instance.

| Total shared running hours / 30 days | RAM + disk before allowances |
| --- | --- |
| 30 | $0.83 |
| 120 | $3.30 |
| 360 | $9.90 |
| 720 | $19.80 |

Actual CPU adds $0.000020 per consumed vCPU-second. Workers Paid includes
25 GiB-hours RAM, 200 GB-hours disk and 375 vCPU-minutes, shared at account level.
The table excludes those credits, the existing $5 Workers plan, Worker/DO usage,
network, logs and graph storage/build costs. The Container's coordinator DO can
also accrue duration while active. This is a usage model, not a measured invoice;
traffic volume and account-wide allowance consumption remain unknown.

## Transit and mode implications

The existing HK PBF includes 54 subway, 31 light-rail, 12 tram, 53 ferry, 1,788 bus
and one train route relation. These include directions/variants and may include
boundary context; they are not counts of unique HK services.

The downloaded Transport Department GTFS has 2,402 bus/minibus routes, 59 ferry
routes, six tram routes and one funicular route. It includes MTR Bus but no MTR
subway/heavy rail. OSM supplies MTR topology; rail service timing and station
transfer/access validation still need separate sources. The official
[MTR lines/stations data](https://opendata.mtr.com.hk/data/mtr_lines_and_stations.csv)
and [Next Train API](https://opendata.mtr.com.hk/doc/Next_Train_API_Spec_v1.7.pdf)
are useful starting points, not proof of a complete static journey-planning feed.

The walking cross-harbour result already traverses an OSM ferry edge, but its
estimate does not include a verified departure timetable. Future passenger bus,
MTR and ferry results need scheduled/frequency service, transfers and access walks.
Native bus-vehicle costing does not provide passenger transit planning.

Keep an engine-independent itinerary/leg contract. Benchmark native Valhalla's
GTFS multimodal support against a dedicated planner such as OpenTripPlanner
after feed coverage is established. The tested WASM SDK exposes only walking,
cycling, car and truck; scooter/transit support would require additional work.
